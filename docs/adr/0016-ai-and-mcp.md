# ADR 0016: AI and MCP

Status: accepted, 31 October 2026 (Phase 7)

## Decision

- **Off by default, and only ever proposes.** AI and MCP are switched on by the owner in Settings. Every feature has a fallback that works without AI, and with every switch off the app is exactly as it was in Phase 6. Nothing AI or a connected app produces acts: it becomes a row in `proposals`, shown as a card on Approvals, and a parent's tap runs it through the same commands as Control's buttons and the Approvals screen, as that parent and with that parent's rights. Carers can approve a Pause or a yes to a request, never an Allow or Block. A card lapses after 30 minutes. No AI on the kiosk, none that talks to a child.
- **One gateway** (`packages/ai`, `invoke`). Checks in order, cheapest first: feature known, master switch, feature switch, provider chosen, data level allowed for the provider, model on the provider's list, monthly limit. A refusal is a result, never a throw, so every caller falls back. Every call and every refusal is a row in `ai_calls` (feature, provider, model, tokens, estimated cost in hundredths of a penny, data level); prompts and replies are never stored.
- **Providers**: Anthropic, OpenAI, Google (refused unless the owner marks the key as on a paid plan), Mistral, Amazon Bedrock (session credentials, `eu.` inference profiles), and Ollama through the OpenAI-compatible provider, at an address the owner gives. Ollama can also run in the stack with the `ai-local` profile (added in Phase 9, as brief Part 16 asks): off by default, on the internal network only, reached as `http://ollama:11434/v1`.
- **Keys** are sealed with AES-256-GCM under `secrets/master_key` (made by `init.sh`), with the household and provider as associated data, so a sealed key cannot be moved to another row. They are write-only in Settings (last four characters shown) and never logged or audited. No master key, no AI and no MCP: fail closed.
- **Data levels.** 1 (totals, job titles, app names) goes to any provider. 2 (what a parent types) only when switched on for the feature, with children's names replaced by "Child A" and put back on the way in. 3 (photos, DNS logs, a child's own answers) never goes to a cloud provider. The week note is built from totals, never the Sunday answers.
- **Untrusted content** (the weather service's answer, anything typed) goes into prompts as quoted `<data>`, and every model answer is parsed against a Zod schema and checked against the family's own children, apps and durations before a card exists. The flows that read untrusted content have no tools, and the MCP tools never return a note a child typed, since the same session can propose.
- **MCP server** at `/mcp` on the main api, behind Caddy: `@modelcontextprotocol/server` 2.4.0, streamable HTTP, protocol 2026-07-28 only (2025-era requests are refused), JSON answers, one server instance per request. Read tools (scope `read`): `get_status`, `get_week`, `get_history`, `get_pending_approvals`. Propose tools (scope `propose`): `propose_override`, `propose_pause`, `propose_approval`; each asks the person to confirm through a multi-round-trip elicitation, with the arguments carried in request state signed by the SDK's HMAC codec (key derived from the master key, five minutes, bound to the method, the app and the person), and only makes a proposal. The SDK checks the `Mcp-Method` and `Mcp-Name` headers against the body. Every tool call is audited.
- **OAuth 2.1, with this platform as the authorisation server.** Metadata at `/.well-known/oauth-authorization-server` and `/.well-known/oauth-protected-resource/mcp`. Public clients identify themselves with a Client ID Metadata Document: an https URL the server fetches (public addresses only, checked inside the connection's own lookup so the address checked is the one used; no redirects; 5 seconds; 16 KB, counted as it arrives). An allowed app keeps the name the owner saw, and needs allowing again if its return addresses change. The authorisation endpoint is a screen in the parent app: the parent signs in with their passkey as usual and says yes or no. The owner's yes also lets the app in for the household; other parents can only connect apps the owner has let in; carers cannot connect apps. Codes last a minute and work once, with PKCE S256 only. Access tokens last an hour; refresh tokens last 30 days, work once and are replaced, and a reused one ends every token from that sign-in. All codes and tokens are stored as SHA-256 hashes. Every request re-checks the token, the app (still allowed) and the person (still active, still a parent). The owner removes an app in Settings, which revokes its tokens at once; switching connected apps off revokes every app's tokens.
- **MCP client**: the weather for job ideas, from an MCP server the owner adds and approves, calling only the tool and arguments the owner set, over https, with a 5 second limit and the answer cut to 600 characters.
- **Routes for bearer clients** use a new access level, `token`: the access hook reads no cookies and checks no Origin for them, and the route checks its own bearer token or grant. Only `/mcp` and `/oauth/token` use it. The token endpoint alone accepts form bodies.
- **Network**: the api joins the `egress` network, so it can reach AI providers, client metadata documents and the weather service. It publishes nothing on it.

## Why

Brief Parts 13 and 22 (AI only proposes, and every write is a proposal a parent approves), Part 8 (secrets as files, fail closed), and the reuse report (the gateway pattern). The MCP 2026-07-28 revision replaces server-to-client requests with input-required results, which fit a stateless, per-request server behind Caddy.

## Consequences

- An assistant connected over MCP sees children's names and status: that goes to the assistant's company. The consent screen and the help say so; it is the parent's choice, like any other app they sign in to.
- MCP clients that only speak the 2025 protocol cannot connect. When the main assistants move to 2026-07-28 this matters less; if one does not, a legacy path can be added behind `isLegacyRequest`.
- The client metadata fetch starts as soon as a signed-in parent opens a consent link, before any tap. It can only reach a public https address and reads at most 16 KB, so the worst a hostile link does is make the server fetch a small document once.
- The api is on the egress network all the time, which also gives it a route to the home network (the owner's Ollama lives there). Only owner-set addresses (Ollama, the weather service) and public addresses (providers, client documents) are ever called.
- Cost is an estimate from list prices in `packages/ai/src/providers.ts`. A provider changing prices makes the limit approximate until the table is updated.
- The master key now seals AI keys. Losing `secrets/master_key` means pasting the keys again; it does not lose any family data.
