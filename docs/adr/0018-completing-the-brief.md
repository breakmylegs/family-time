# ADR 0018: Completing the brief

Status: accepted, 8 November 2026 (Phase 9)

## Context

A walk through the brief, part by part, found items no phase had finished (docs/plans/phase-9.md). This records how each was built, and the choices that differ from the plan's first words.

## Decision

- **Stopping points** (the transitions phase, research section 6). The control engine gives a planned session or an Allow that ends on its own a few minutes of "finishing up" before the block: a household setting, 5 minutes by default, 0 to 15, 0 off. It sits after bedtime, school and wind-down in the precedence, so it never runs into any of them (protect sleep first), and a Pause or Block still wins at once. A session or Allow a parent ended early (Normal, Undo), or used Block or Pause on while it ran, gets none. Control shows the session's own end as "allowed until", and Finishing up only while the extra minutes run. The minutes are not charged to the week. The kiosk shows "Finishing up" with the time screens go off, not a countdown, because countdown warnings were linked to more upset.
- **The whole family** (research principle 7). Each parent gives their own leisure screen time for the week (self-reported, never measured); Family shows the last four weeks; the kiosk shows only the grown-ups' total. One family challenge at a time, set by a parent, ticked by anyone (a carer on the phone, a child on the kiosk), up to its target and no further. No points, no streaks, nothing lost. Three new tables, all additive (migration 0013), all in the export.
- **Set-up for the owner** (brief Part 9). Devices, each child's rule for each group, which group an app is in, and schedules, on `system.manage`, through the same functions the command line's `device-add` now uses, each audited, each waking the reconciler. A device is removed by marking it (`removed_at`, migration 0014), so its usage history stays; the reconciler, still the only writer to AdGuard, deletes that device's `ft-` client by name and touches nothing else. Schedules allow one per weekday per child (or household) and one bedtime a day, because the engine takes the first match.
- **Alerts** (brief Part 12). The worker asks AdGuard's status on every reconcile tick; three unwell minutes in a row (not answering, not running, or protection off) alert owners and parents once, and its recovery once more. An hour before the week resets, while the economy is on, parents are reminded the family review is ready, once a week.
- **Readiness** (brief Part 15). `/readyz` adds `adguard` (its admin API answers at all, so a fresh install is ready before `adguard-setup`) and, with the Besu ledger, `besu` (the worker reached the node in the last two minutes, read from `worker_heartbeat.chain_seen_at`, migration 0015, because the api has no route to the node; passes before a contract exists). Because readiness now needs AdGuard, `update.sh` starts AdGuard, and Besu or Ollama when their profiles are on, before the api; before this, they started only with systemd at boot.
- **Matching on the savings goal** (brief Part 6). The plan said "on each payout". It is instead **at the week's close**: the parents add their percent of the pocket money earned that week (jobs, conversions and the unused-time bonus), as their own MONEY award "Matched by Mum and Dad", never more than the goal still needs. One entry a week through its reference, every earning route counted without code in each, and nothing tied to when money is handed over. Changing a goal's price or match keeps its bar; a new title starts a new one.
- **Local AI** (brief Part 16). An `ollama` service behind the `ai-local` profile, `ollama/ollama:0.40.15`, on its own internal network shared only with the api (the api's default address `http://ollama:11434/v1`), with no route out, all capabilities dropped, nothing published, and models in their own volume outside backups. `./scripts/ft.sh ollama-pull MODEL` downloads one through a one-off `ollama-pull` container, the only Ollama with egress, and only while it runs. Ollama's cloud models are refused by `ft.sh` and by the api, because Ollama counts as local and so may receive the most private data. Profiles stay in `deploy/.state/ledger.env`, which may now hold `ledger-besu`, `ai-local` or both. An Ollama elsewhere on the home network still works (ADR 0016).
- **ADR 0014 follow-ups.** Account permissioning: a one-off `besu-allowlist` service (the Besu image, no network, the signer key secret) writes the signer's address to a volume, and Besu accepts transactions from that account only; the node itself still never holds the signer key. The admin key: `ft.sh ledger-deploy` records that it has been used (`deploy/.state/ledger-admin.env`, which the keys backup and `restore.sh --keys` carry to a new server), and `init.sh` then never makes a new one.

## Consequences

- More of the owner's set-up moves off the command line; the command line keeps working for everything, and stays the way in when the app cannot be reached.
- A parent's own screen time is on the kiosk as a total. Parents who would rather not share it simply leave it blank.
- AdGuard down now makes the api not ready. A failed deploy because AdGuard is down rolls back the api, which does not fix AdGuard; the log says which check failed.
- Still not built, with reasons, in docs/plans/phase-9.md: the monthly wellbeing check (licence), owner OIDC, kiosk HTTPS on the LAN and router rules (the owner's network), and the on-chain contract changes (next contract version).
