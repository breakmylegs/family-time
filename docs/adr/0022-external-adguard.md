# ADR 0022: The household's own AdGuard by default

Status: accepted, 22 November 2026. Amends [ADR 0010](0010-adguard-ownership.md).

## Context

The pilot server is a Proxmox VM on a home network whose AdGuard Home already runs separately, managed by another setup. A second AdGuard in Family time's stack would mean two DNS servers, a port 53 clash on the LAN address, and settings changed on a DNS server the family did not ask Family time to run. V2 households will often have an AdGuard already, too.

## Decision

- **Two modes, external by default.** `deploy/.state/adguard.env` holds `ADGUARD_MODE` (`external` or `bundled`), `ADGUARD_URL`, `ADGUARD_USER`, `ADGUARD_CA` and `ADGUARD_ALLOW_UNTESTED`. `init.sh` writes it from flags or questions, and keeps it on a later run unless told otherwise. Every script reads it the same way, by `load_adguard_env` in `scripts/lib/deploy-lib.sh`: parsed, never run as shell, each value in a known shape, like `backup.env`. An install from before this ADR that still has the bundled AdGuard's volume stays bundled.
- **The bundled AdGuard is a Compose profile, `adguard-bundled`.** It only starts, and only publishes `LAN_IP:53`, when chosen. `compose()` adds the profile; `update.sh` starts it by name only then, and never runs a bare `up -d`. The systemd unit goes through the same `compose()`.
- **External AdGuard is reached over `egress`**, the network the api and worker were already on, so any address the server reaches works. Nothing is published for it. `https` is the recommended address; `http` works, with a warning from `init.sh` and every `update.sh`, because AdGuard's login (Basic auth, once a minute, no roles) then crosses the LAN in the clear, where a device on the same Wi-Fi could take it and control the home's DNS. The docs ask for https, a user and password of Family time's own, and a wired network.
- **A self-signed certificate is trusted for AdGuard only**, when the owner opts in (`init.sh --adguard-ca FILE`, `ADGUARD_CA=1`). The AdGuard client gets its own fetch (`node:https` with `ca`, `packages/adguard-client/src/tls.ts`); every other connection in the api and worker keeps the usual trust, so the certificate's key can never stand in for the sign-in service, AI providers or push services. `NODE_EXTRA_CA_CERTS`, which would trust it process-wide, is not used. `init.sh` refuses a CA certificate or a bundle, and stops trusting a certificate when the address changes. Certificate checks are never switched off.
- **The password is a file, never an argument.** `secrets/adguard_password` is written from a hidden prompt or standard input (`--adguard-password-stdin`). `update.sh` gives it to curl on standard input, so it never appears in a process list or log.
- **Checked before every deploy.** In external mode `update.sh`'s preflight checks from the server that AdGuard answers, the login works and the version is supported, and stops before anything is built if not, with what to do. After the start, `/readyz` shows the containers reach it too.
- **Version policy: a tested series, not one exact version.** The client is contract-tested against v0.107.79. A later 0.107 patch is accepted with a note, because AdGuard has kept its 0.107 control API compatible across patches and the reconciler reads back every write. An older version is refused: the fields Family time writes are tested from v0.107.79 up. A newer series (0.108, 1.x), where a breaking API change would land, is refused unless the owner sets `ADGUARD_ALLOW_UNTESTED=1`. The running worker never stops on version; a difference in how AdGuard stores what Family time writes shows as Not confirmed on Control. The rule lives in `packages/adguard-client/src/version.ts` and, for the preflight, in `deploy-lib.sh`; a test keeps their tested versions equal.
- **`adguard-setup` on an AdGuard it does not run.** It never runs the first-time wizard on an external AdGuard. Its dry run lists each global setting it would change, as it is now and as it would be; `--yes` applies them. `--family-time-only` leaves every global setting alone and records the household setting `adguard_scope = family-time-only`: the reconciler then writes only between markers the owner added by hand, and never adds them, so a missing block is an error with the exact lines to add, not a block appended to someone else's rules.
- **Backups.** `backup.sh` and `restore.sh` copy AdGuard's volume only in bundled mode, and otherwise say AdGuard is backed up wherever it runs. After a restore, the reconciler writes Family time's clients and rules back within a minute.
- **The contract tests never touch the live AdGuard.** They run only against the throwaway AdGuard in the test project; `scripts/test-pg.mjs` refuses any other address.

## Consequences

- ADR 0010's rule is unchanged: at runtime the worker is the only writer, whichever AdGuard it is, and the only other writer is `ft.sh adguard-setup`, which the owner runs in the api image. The api's running code only reads.
- The api, which faces the internet, holds the AdGuard password (it reads the query log for the discovery helper). With an external AdGuard that password controls the whole home's DNS, so code running in the api could change it. Moving those reads and `adguard-setup` behind the worker, so the long-running api holds no AdGuard password, is a later change.
- "Confirmed" proves AdGuard holds Family time's `ft-` client and its rules block, and that no allow rule lets one of the device's blocked services through: after each write the reconciler asks `/filtering/check_host` about one domain of each blocked service, for the device's IP or ClientID (at most 12 a device a minute). Only an explicit allow (`NotFilteredWhiteList`) makes the device Not confirmed, naming the rule; any other answer, or none, is no finding, so a quirk of AdGuard's check never marks a device wrongly. The contract test proves the allow answer against the real v0.107.79. A device known only by its MAC is not probed.
- Moving from bundled to external: `update.sh` removes the old bundled AdGuard container, and `verify.sh` reports DNS still answering on the server.
- The systemd unit runs `scripts/stack.sh`, which reads the deployed tag strictly rather than running `image.env` as shell.
- Family time can no longer promise AdGuard's caching settings in external mode with `--family-time-only`; the docs ask the owner to keep answers cached for a minute at most.
- The household's AdGuard sees Family time's `ft-` clients and rules alongside its own. Family time never touches a client whose name does not start with `ft-`, or any rule outside its markers.
- Existing servers must re-copy the systemd unit (docs/setup/server.md).
